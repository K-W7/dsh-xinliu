# dsh-xinliu · 心流

> 把心里说不清的想法，逐条问清、记下理由，压成一份能开工的框架；卡住了它会追问，不假装顺利。

**v1.0.0** · MIT · DSH 0.2.x · Node `^22.19.0 || >=24.0.0`

---

## 先说清楚：它跟"端"没关系

心流**不是鸿蒙插件，也不是桌面组件**——它是一个纯 JS 的 DSH host 插件，只依赖 DSH 0.2.x 提供的三样东西（`systemPrompt` / `tools` / `commands`），不碰系统 UI、不调任何端特有 API。

- 「把想法问清、压成框架」这件事本身只发生在**对话**里，产出是两份 Markdown + 一份 JSON；
- 所以桌面版能跑、网页版能跑、手机端能跑、自建的 headless 也照样能跑——**只要那个宿主是 DSH 0.2.x**；
- 换端只是换一个 DSH 宿主：把数据目录（默认 `~/.dsh/xinliu`）带过去，流程和记录接着走；
- 鸿蒙 DSHM 只是"其中一个端"，用法与其它端完全一样，没有特殊分支。

> 一句话：**它不是某个平台的产物，它是一套"把想法敲定"的流程 + 六个工具 + 两份可带走的文件。**

## 它做什么

一条「心流」= 一次把想法敲定成框架的过程。它做四件事：

1. **提议**：你抛出想法，它问一句「要不要开成一条心流」，你点头才开。
2. **多角色先想一遍**：按项目类型挑 3–5 个立场，红队常驻（专门挑毛病）。
3. **三种记录**：已定（结论 + 理由 + 怎样算对味）、待定、障碍（已发现未解决的坑）。
4. **锁版**：7 节齐全、每节有对味判据、无障碍未认领，才能锁；锁不锁由你点，它不替你决定。

## 产出两份文件

| 文件 | 规则 |
|---|---|
| `当前框架.md` | 锁版时由 `flow.json` 渲染，**手改会被覆盖** |
| `决策日志.md` | 只追加，一行一条：时间 · 类型 · 内容 · 理由 |

## 七个章节

一句话定位 / 给谁用·什么场景 / 功能清单（必须有·可以砍·不做）/ 交互与入口 / 数据与隐私 / 风险与对策 / 里程碑与验收。

每节都必须带一句「**怎样算对味**」，否则锁版会被拒绝——这是进入验收（闸二）的入口。

## 工具与命令

| 工具 | 用途 |
|---|---|
| `flow_open` | 开一条心流（同一时间只能一条） |
| `flow_settle` | 敲定一节（结论 + 理由 + 对味判据） |
| `flow_defer` | 记一条待定 / 用 `resolveId` 销掉一条 |
| `flow_obstacle` | 记一条障碍，或更新状态/认领人 |
| `flow_status` | 看进度（只读） |
| `flow_lock` | 锁版并渲染框架 |

命令：`/flow start <名字>` · `/flow status` · `/flow lock` · `/flow reopen` · `/flow drop` · `/flow help`

## 安装（任何端通用）

心流是 bundle 型插件（`dsh.bundle.patch` 指向 `cordis.patch.yml`）。下面两种方式在所有端通用，把 `<profile>` 换成你实际用的 profile 名即可。

### 方式一：走插件管理器（推荐）

```powershell
dsh plugin --profile <profile> add --offline "file:<绝对路径>/dsh-xinliu-<版本>.tgz"
```

- 桌面版也可以在侧栏「Plugins」页里安装同一个 tgz；
- 手机端（如 DSHM）在设置→插件里装，或走推送安装；
- 装完 DSH 会热挂载新的 bundle：**工具表里出现 `flow_*`、或提示词里出现「心流」一句，才算真的活着**（安装日志不算）。

### 方式二：直接铺进 profile（不经包管理器）

1. 把本目录复制到 `$DSH_HOME/profiles/<profile>/node_modules/dsh-xinliu/`
2. 在该 profile 的 `cordis.patch.yml` 末尾追加：

```yaml
- insert:
    - id: dsh-xinliu
      name: dsh-xinliu
```

3. 重开 DSH（或让 profile 重新加载）。

> 这走的正是 profile patch 的官方扩展点（`{insert: […]}` 是追加）。改动前请备份该文件。

### 装完为什么有时"没生效"

- **新装一个 bundle**：热挂载即可用；
- **改过插件 JS 代码**：必须重启 DSH——Loader 按 specifier 缓存 ESM 模块，`remove+add` 也不会重新导入同一路径；
- 判活只看运行时证据（工具表 / 注入的提示词 / 命令存在），不看安装日志。

## 数据

- 根目录：`$DSH_XINLIU_DIR` 或 `~/.dsh/xinliu`
- 每条心流：`flows/<id>/flow.json`（唯一数据源）+ `当前框架.md` + `决策日志.md`
- 指针：`current.json` 记录"正在进行的那条"
- **全在本机，不联网、不遥测**；换端时把这个目录带走即可接着用

## 与上游 1.0.0 的差异

上游 1.0.0 在 DSH 0.2.x 上有个契约问题：`export const inject = ['systemPrompt']` 漏了 `'tools'`，而 `tools` 是注入服务 → `ctx.tools.register` 抛错被 catch，结果是**只注入提示词、六个 `flow_*` 工具一个都不注册**。

本包修的就是这一行：`inject = ['tools', 'systemPrompt']`（见 `index.mjs`）。npm 上的 **1.0.0 已经带着这个修复**，装下来就能用，不需要再打补丁；早期本机补丁 `1.0.0-klrsl.1` / `1.0.0-klrsl.2` 只留在 `E:\DE\_ci-logs\packs\` 里，不再发布。

## 开发

```bash
node --test tests/    # 状态层单测：开流/并发/敲定/锁版校验/待定/障碍/日志/坏文件/重开
```

| 文件 | 职责 |
|---|---|
| `index.mjs` | host 半区：提示词、六个工具、`/flow` 命令 |
| `lib/store.mjs` | 状态：开流、敲定、待定、障碍、锁版校验、日志追加 |
| `lib/template.mjs` | 7 节模板、章节名归一化、按项目挑角色 |
| `lib/render.mjs` | 框架文档与日志行渲染（纯函数） |
| `tests/store.test.mjs` | 状态层单测 |

## 路线

- **v1.0（本版）**：闸一全套（提议 / 记录 / 停滞检测 / 锁版 / 两份文件）。
- **v1.1（M2）**：红队升级为真智能体（真分歧才拉）、模板按项目类型切换。
- **v2.0（M3）**：闸二——验收清单 + 对味逐条对，不过就回闸一。

## 边界

- 不做开发进度、任务拆分、验收（v2.0 才做闸二）。
- 不保留框架文档历史版本；想查"当初为什么这么定"看决策日志。
- 不做常驻界面/桌面组件——不是受某个平台限制，而是本插件只提供流程与工具，任何端保持同一套行为。
- 未开启敲定模式时只有一行提示词，不做流程约束。
